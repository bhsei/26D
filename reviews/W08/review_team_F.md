| Y1  | §4.2 (inspection fails), §4.1, FR-REQ-07, FR-REQ-08            | Inconsistency | Severe   | In §4.2 the owner approves the request first, and then a failed inspection makes the system reject it. But the state diagram in §4.1 has no Approved to Rejected change, FR-REQ-07 allows reject only while the request is Pending, and FR-REQ-08 says these are the only allowed status changes. So the main flow breaks the lifecycle rules. The code works in a different order: a failed inspection is accepted only while the request is still Pending (`reject_equipment_inspection`), and the owner's approval is the last step, after both inspections and the payment (`approve_request`). So §4.2 does not describe the real flow either.                                                               | Change §4.2 to the real order: meetup and inspection while the request is Pending, then the payment, then the owner's approval as handover confirmation. Then §4.1, FR-REQ-07 and FR-REQ-08 stay correct, and "Approved" has one clear meaning. | Yasmine  |
| Y2  | §4.2, steps from "Schedule meetup" to "Start rental countdown" | Missing       | General  | Seven steps of the main flow have no requirement in §3.2: confirm meetup and inspection, report a failed inspection, confirm inspection approval, upload photos of the item condition, confirm readiness, confirm handover, and start the countdown. Only the countdown is close to a requirement (FR-REQ-10). The other steps appear only as prototype gaps in Appendix A, although the application already implements them (the code has meetup and inspection fields and refuses handover without both inspection approvals). So the flow cannot be traced to requirements. See also H2, which describes the same missing steps from Appendix A.                                                               | Add a requirement (ID, priority, status) for each step, or remove the step from the flow if it is not planned. Write the requirement IDs next to the steps of the diagram.                                                                      | Yasmine  |
| Y3  | §4.2 (deposit steps), FR-PAY-02, FR-PAY-06, FR-PAY-07          | Inconsistency | General  | There are two differences. First, in §4.2 the borrower pays the deposit and the system records it, but FR-PAY-02 says the owner marks the deposit as Held. (The code lets only the owner confirm the deposit, so FR-PAY-02 matches the code and §4.2 does not.) Second, for a damaged item §4.2 refunds the remaining deposit after the damage charge, but FR-PAY-06 allows a refund only when the condition is Good Condition, and FR-PAY-07 only says the charge is applied. The rule for the remaining deposit after damage is not written in any requirement.                                                                                                                                                 | Say who does each deposit action. Add or change a requirement for the refund of the remaining deposit after a damage charge. Then make §4.2 and §3.2.5 say the same.                                                                            | Yasmine  |
| Y4  | §4.1 (Approved to Overdue), FR-REQ-08, FR-PAY-09               | Inconsistency | General  | The same behavior (a rental becomes Overdue after the end date) is in two requirements with different values: FR-REQ-08 is Must / Testing and FR-PAY-09 is Should / Not Done. Also, §4.1 shows this change as normal behavior, and the status of FR-PAY-09 (Not Done) seems out of date, because the code already has a function that sets Approved rentals to Overdue after the end date (`mark_overdue_rentals`). FR-REQ-08 also lists five status changes in one requirement, so one status cannot describe it.                                                                                                                                                                                                | Keep one requirement for the automatic Overdue change, with one priority and one status. Split FR-REQ-08 into one requirement per change, or mark the not implemented change in the diagram (for example a dashed arrow with a note).           | Yasmine  |

FR-EXT-02 (relational database) is a design constraint, not an interface. Photo storage, the scheduled scripts and the simulated QR payment link have no interface requirement. FR-EXT-01 says "for all functions" and no requirement names the supported browsers (NFR-USE-03 only gives a minimum screen width, and NFR-POR-01 is about the server system), so a demonstration cannot show that it is met. There is also no behavior for an unavailable interface, for example when the SMTP service is down. | Write one requirement per interface of §2.1: what is exchanged, in which direction, and what the system does when the interface is not available. Move FR-EXT-02 to the constraints in §2.5. In FR-EXT-01 name the supported browsers.          | Yasmine  |
