| # | Location | Type | Severity | Finding | Recommendation | Reviewer |

| 1 | §7.1, state diagram `connection_state_machine.png` | Inconsistency | Moderate | The diagram has fewer transitions than the text of §7.1–7.2 and the SRS. Error can only be reached from Connecting and Connected, and it only leads to Unknown. Unknown only leads to Disconnected, although the note says that a fresh query may confirm Connected or Error. Missing are: Disconnecting → Error; Connected → Disconnected when the adapter reports that the tunnel stopped (UC-01 7a, UC-08 step 3); Connecting → Disconnected after a denied permission (E-CONN-01); and Error → Connecting for the retry that the user confirms (E-CONN-04, UC-08 step 5). | Add the missing transitions with their events, or add a table (from state, event, to state) next to the figure. Check each row against E-CONN-01 to E-CONN-04 and UC-08. | Borja |
| 2 | §7.1, table of the operation status and figure | Missing | General | The operation status (Idle, Validating, AwaitingPermission, RequestPending, Rejected, TimedOut) is a second state model, but it is only a list and a note in the figure, without transitions. We cannot see which status follows which (for example RequestPending → TimedOut → fresh query → Unknown) or when it goes back to Idle. The rules of §7.2 (one operation in flight, duplicate taps ignored) are not linked to it. | Draw a second state diagram for the operation status, with events and guards, and show how TimedOut and Rejected act on the lifecycle state (fresh adapter query, last confirmed state kept). | Borja |
| 3 | §5.1 and §5.2, Level 0 and Level 1 diagrams | Inconsistency | General | The figures do not match the tables. Level 0: F-08 (optional control plane) is in the table but the figure has no entity or flow for it; F-02 and F-03 are two flows in the table but one double arrow in the figure; F-06 is read and write in the table but the arrow goes only to D2 (F-05 also goes one way only). Level 1: P1 is in the table but not in the figure, and lane P7 has no input from P4, P5 or P6, although the table says that P7 receives the domain result and the adapter state. | Draw F-08 and the control plane, one arrow for each flow with its direction, and the inputs of P7. Show P1 in the figure or add a note in each lane. | Borja |
| 4 | §8.2 and §8.6, with §5.1 (F-04, F-05) and §5.2 (P4) | Ambiguity | Moderate | It is not clear which of the 11 entities of §8.2 are stored in Core Release 1, and where. §8.6 says that history is off by default and that diagnostic results stay in memory, and §5.2 says that recommendation results are stored only if approved, but §8.2 calls all 11 entities Core Logical Entities. The data-flow design has no store for the endpoint catalogue: F-04 goes only to the client and D1 holds only settings, profile metadata and optional history. Yet `ENDPOINT` is referenced by sessions and candidates, and §5.6 and §8.4 speak of cached and stale data. | Add a column Core Release 1 storage to the table of §8.2 (D1, D2, memory only, not stored) and show the cache of the catalogue in the data-flow diagrams. | Borja |
| 5 | §8.2, and §8.6 | Missing | General | Only §8.4 (measurement) and §8.5 (recommendation result) list attributes. `APP_SETTINGS`, `CONNECTION_PROFILE`, `ENDPOINT`, `CONNECTION_SESSION`, `DIAGNOSTIC_RUN`, `DIAGNOSTIC_RESULT` and `METHOD_VERSION` have only a purpose and a key. The fields of the session summary are in the History screen of Part II, and §8.6 only says approved session-summary fields. Chapter 8 has no data model diagram; the ERDs in `docs/DeGlitch_v1.5_diagrams/` are not referenced from the document and show only entity names and cardinalities. | Add a table of attributes (name, type, required, example) for each entity and a diagram with keys and cardinalities in §8. Use the same session-summary fields in §8 and in the History screen. | Borja |
| 6 | §8.2.1, §8.4, §8.5 and §5.4 | Inconsistency | General | Names and values are not the same. (a) The key of a measurement is `measurement_id` in §8.4 and `observation_id` in §8.2.1 (`NETWORK_OBSERVATION`, `RECOMMENDATION_INPUT`). (b) A check is `measured` in §5.4 and DD-02, but `availability` in §8.4 has Available. (c) §8.5 has a list `ranked_endpoint_ids`, while §8.2.1 has `RECOMMENDATION_CANDIDATE` with its own key and rank. (d) `accepted_by_user` cannot say dismissed or no action, which the recommendation ERD shows. (e) §8.2.1 says that an observation or a diagnostic run may have zero or one session, but ERD_core shows 1 to many from the session. | Use one name and one set of values for each item (for example `measurement_id` and the same outcome values in §5.4 and §8.4), replace `accepted_by_user` with a decision value, and make the ERD cardinalities the same as §8.2.1. | Borja |
| 7 | §7.1, `TimedOut`, and §7.3, E-DIAG-01 | Missing | General | Chapter 7 has no time limits. `TimedOut` is an elapsed operation deadline but the deadline is not given, E-DIAG-01 has no probe timeout, and the delay from adapter event to visible state of REQ-REL-001 (proposed 2.0 s, decision D-09) is not mentioned in §7. D-15 is cited only in §6.7. Without a value or a safe default the state model cannot be tested. | Give a proposed value for the connection operation, the probe and the delay of the visible state, marked as pending D-09 and D-15, or refer to D-09 and D-15 and their safe default in §7.1 to §7.3. | Borja |
| 8 | §5, §7 and §8, traceability | Traceability | General | Chapters 5, 7 and 8 do not cite any use case or requirement ID. Appendix B maps UC-01 to UC-12 to section numbers only, and REQ IDs appear later, in the screen tables. So we cannot check that each state, each error E-xx and each entity comes from a requirement, for example REQ-FUNC-001 and UC-08 for the states, or REQ-FUNC-011 and UC-07 for the session summary. | Add a column Requirements and use cases to the tables of flows (§5.1), states and errors (§7.1, §7.3) and entities (§8.2). | Borja |
| 9 | §9.1.1, adapter operations | Missing | General | The adapter contract gives the fields of each operation but not its results or time limits. `connect` "returns acceptance separately from state", but the accepted, rejected or busy values are not listed, and no operation has a timeout. The failures are not linked to the error codes of §7.3 (E-CONN-xx). | Give the result values and the timeout of each operation, and the E-code that each failure produces. | Alfonso |
| 10 | §9.2, Authorized Endpoint Source | Ambiguity | Moderate | §9.2 lists fields and response states, but not the operation that the client calls, its input, or where the catalogue comes from in Core Release 1. §9.3 says the control-plane API is only a future proposal, so UC-03 has no defined source. | Add an operation table like §9.1.1 (for example `listEndpoints()` with its result states) and say where the Core Release 1 catalogue is read from. | Alfonso |
| 11 | §9, Lite Mode | Missing | General | C-LITE (§4.2) uses a "platform capability" to pause background jobs and animation (REQ-LITE-001..003), but chapter 9 has no interface for it. The adapter of §9.1 only covers the tunnel. | Add the platform interface that C-LITE uses (operations, unsupported result), or say in §9 that Lite Mode only uses internal app settings. | Alfonso |
| 12 | §15.2, design tokens, and §18.1 | Inconsistency | Moderate | Some tokens fail the contrast of §18.1 (4.5:1 for normal text) on the page background `#F5F9FE`: muted text `#7889A8` gives about 3.3:1, primary blue `#087CF0` 3.9:1, error `#D9515B` 3.8:1, success `#18A66A` 3.0:1 and warning `#E9A43A` 2.0:1.
